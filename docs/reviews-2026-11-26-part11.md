§02　FlClash 的字体链路，一条一条贴
第一条，它自带什么。pubspec.yaml 第九十一到九十七行，两个家族：JetBrainsMono 带一个 273,900 字节的 ttf，Twemoji 带一个 1,454,532 字节的 ttf。lib/ui/fonts.dart 的枚举只有这两个值。也就是说它自带的字体里没有一个汉字〖900〗，也没有任何 CJK 字件。
第二条，它怎么选字体。lib/manager/theme_manager.dart 第三十六到四十六行，ThemeData 里两个参数：fontFamily 来自 themeSettingProvider，默认是 null；fontFamilyFallback 来自 package:prism_ui 的 appFontFamilyFallback。默认 fontFamily 为 null，意味着引擎用平台默认族。
第三条，Android 上那个 fallback 返回什么。它自己的测试写死了这条行为，test/common/font_test.dart 第八十九到九十七行，测试名就叫"leaves Android to its own locale-aware fallback"，断言 fallback(android, [en]) 是空表，而给个 fontFamily 为 serif 时返〖1000〗回 ['Roboto']。空表的意思是把回退完全交给系统。
第四条，它读不读系统字体清单。读。lib/common/system_fonts.dart 调 rust_api.systemFontFamilies，实现在 plugins/rust_api/rust/src/fonts/android.rs 第一到六行：FONTS_XML 常量写死 "/system/etc/fonts.xml"，read_to_string 之后取所有 <family name="..."> 的 name。它只取命名族，匿名族它看不见。
这四条合起来的结论是：FlClash 在 Android 上默认用平台默认族，也就是 sans-serif，而 sans-serif 正是我这几轮在插的那一族。所以〖1100〗"插 sans-serif 对 FlClash 应该有效"这个推理是成立的，而主人实测没变。矛盾就出在这里，剩下的三条可能我上一轮就列过，这一轮又收窄了一层。
§03　矛盾的三条可能，和那个零成本判定
甲，ColorOS 十七的 Skia 不读 /system/etc/fonts.xml。我手上的证据全是 AOSP 的 Skia 源码，LMP_SYSTEM_FONTS_FILE 那行常量、append_system_font_families 的读法，都是 AOSP。ColorOS 改没改这条路，我没〖1200〗有证据。没有证据就是没有证据，不许拿 AOSP 的行为推断 ColorOS。
乙，读到了，但我们的字件被建成第二个同名的族。Skia 源码注释里明确写过一件事：customizationType="append-to-existing" 这个属性它完全忽略，只看 name，于是会造出第二个独立的同名 FontFamily，结果是遮蔽而不是合并。我插 sans-serif 的做法在 Minikin 那边是合并语义〖1300〗，在 Skia 这边可能变成遮蔽，于是先建成的那个赢得匹配，我的排后面就永远不赢。这一条与主人实测吻合，而且能解释为什么插入行明明在文件里、屏幕上却不变。
丙，FlClash 用的 Flutter 引擎版本里，平台默认族不是 sans-serif。这一条纯属猜测，我把它列出来是为了以后能排掉〖1400〗，不是为了现在用它当借口。
三条里有一条可以零成本判定，而且不需要改任何配置、不需要刷机、不需要 root：FlClash 的设置里有字体选择器，它列的就是 /system/etc/fonts.xml 里的命名族清单（第四条链路证据说明它读这个文件、只取命名族）。打开设置到字体那一页，看列表里有没〖1500〗有我们那两个家族名（Selffont Rounded SC VF 或母版的家族名）。
有，说明文件读到了，甲被排掉，问题落在乙或丙，那就该去查族匹配与引擎版本。
没有，说明甲成立，Skia 这条路对这台机器无效，插入再怎么改都不会变，必须换路：进程内热切换或者整份替换。
这个判定我拖了两轮〖1600〗才想出来，而它只要主人点两下屏幕。这就是我这一串事故的典型形状：我把力气全花在"改我这边的代码"，而不是"找一个能一刀切开的判据"。改代码能做很多轮，判据只要一条。

§07　hotswap 这条路要不要走，我给判断不给选项
hotswap 的实现在 lsp/hotswap/src/main/kotlin/sumicya/selffont/hotswap/Hotswap.kt，一百六十七行，三件事：反射 sSystemFontMap 换家族表、换 Typeface.createFromFile 的返回值、按家族名换 Typeface.create。文档标着"未真机验证"。
它对 FlClash 有没有用？我的判断是没有，理由是 FlClash 是 Flutter 应用，它的文字排版走 libflutter.so 里的 Skia，字体解析不经过 Java 层的 Typeface。hotswap 换的是 Java 的〖2900〗家族表，Flutter 不查那张表。
它对什么有用？对系统界面、设置、微信这类真正用 Java Typeface 的应用有用。而主人的目标一直很具体：让 FlClash 变字。所以 hotswap 不是解，它是另一个产品。
那解是什么？如果判定结果是"甲"（ColorOS 不读 fonts.xml），解只有一条：替换 FlClash 自己的字体资产，也就是改它的 APK 或者用资源覆〖3000〗盖把 assets/fonts 里塞 CJK 字体。这属于改别人的应用，我不做，也不建议做。
如果判定结果是"乙"（同名族被遮蔽），解是把插入方式从"再写一个 name=sans-serif 的族"改成"改写设备原有那一族的字件顺序"，也就是不再新增族、只改已有族的行。这条路技术上可行，但风险是直接动设备的〖3100〗族表，一旦写错就是卡开机，而我上一轮已经卡过一次。
如果判定是"丙"（引擎默认族不是 sans-serif），解是让内置族名对上，但那要改 FlClash，不是改系统。
三条路里没有一条是"再改一轮配置就能好"。这个结论我写在这里，是因为前五轮我一直在默认"再改一轮配置"，而它〖3200〗很可能从一开始就不成立。

§08　为什么不主张继续在配置上打转
把这几轮的账摊开：emoji 改了两轮，卡开机一次；命名族插入改了一轮，FlClash 没变；整份覆盖争议一轮，没有定论。三轮的共同点是，**我每一次都在假设"配置文件被正确解析"**，而从没验过这个假设。验它〖3300〗只需要主人点两下屏幕看字体列表有没有我们的家族名，或者我拿到一条设备上的 dumpsys 输出。这两条我都没做，就直接去改配置。
这是我这一串事故里最该被罚的模式：跳过验证假设、直接优化实现。它比拖拉更隐蔽，因为拖拉是"没做事"，而这个是"做了〖3400〗很多事，全建立在一个没验的假设上"。罚单上写"拖拉"，我猜主人看到的是表象；真正的病是跳过验证。
对治的办法同样只能靠流程：任何改动之前，先写下"这条改动依赖哪个假设"，再写下"这个假设怎么被证伪"。写不出证伪办法的假设，就不许拿它开工〖3500〗。这一条我下一轮开始执行，写在检讨里供核对。
