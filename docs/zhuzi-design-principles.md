# 筑紫 A 丸ゴシック 设计思想小结（给本仓库自己用的操作清单）

这份文档记录的是本仓库对"了/电/国/七/九"等字的几何观察，供改字形时参考；其中经代码或视觉证据支持的原则仍可复用，但不能把历史经验当作不可更改的设计戒律。

**历史说明与当前边界（2026-10-21 修订）**：旧记录曾把"提炼筑紫的统一圆润思想"扩写成"不许直接抄筑紫坐标"的绝对红线，并将其归因于用户。用户明确更正："我没说不能照抄筑紫坐标"，已撤销该绝对禁令及其作为用户指令的归因。当前允许把筑紫作为强视觉/几何基准，并对坐标进行测量与结构分析；本轮选定的目标轮廓应由中心线/参数化方法重建，不逐点照搬筑紫轮廓。该选择限定本轮实现方式，不构成对坐标研究的普遍禁令。

## 1. "逢角必圆"不是"所有拐角都削一刀"，是分三类分别处理

本仓库 `tools/round.py` + `tools/vf_round.py` 实测踩过的坑：把"该不该圆、
怎么圆"按点的真实角色分类，分类错了即使圆角公式本身没错也会出可见缺陷。
三类：

1. **自由端头**（横/竖/撇/捺的真正末端，不跟别的笔画相交）——换成半圆弧
   收尾（`round.py`，`_is_straight_wrap` 判据）。
2. **凸拐角**（同一条笔画自己转弯，比如"国/回"外框自己的四个角）——削成
   圆弧过渡，半径 = `min(两侧边长) * 比例`（不是固定像素值，见下面第 4 条）。
3. **凹角 / T 字交叉口**（两条不同笔画相交留下的切口，比如横竖交叉处的
   内凹角）——**一律不碰**，不产生凸起。这条本仓库从一开始就定了，没有
   例外：`docs/round-preview/history-2026-10-13.md` "T 形接口留下的凹切口...仍然一律
   不碰，不产生凸起"。

**血的教训（"七/九"鼓包 bug，2026-10-15 修复，见 evidence 第 8 项）**：
把第 2 类（凸拐角）误判成第 1 类（自由端头）会把一个正常的转折点削成
突兀的半圆球鼓包——两类用的是完全不同的插值公式（端头是"镶一个半圆"，
拐角是"削掉尖角换一段弧"），公式本身都没写错，错的是分类。**改任何一个
点之前先确认它到底是哪一类，不要假设"看起来像端头就按端头处理"。**

## 2. 转角半径按"相对比例"算，不是写死的绝对像素数

`CORNER_R_RATIO = min(两侧边长) * 比例`，外加一个绝对值上限 `CORNER_R_MAX`
防止长边把半径撑得过大。这条背后的教训：最早用纯绝对半径
（`CORNER_R_MAX=70`），70 单位在实际渲染字号下只有几像素，肉眼根本看不出
是圆角——这是"坐标确实变了，但换算成人眼能感知的视觉效果是另一回事"的
典型案例，数值核验（diff 坐标）跟视觉核验（渲染截图）必须都做，少一个都
可能得出错误结论。半径数值后来参照筑紫"回"字外框拐角的真实视觉跨度重新
量过（约 120–130 单位），不是凭感觉调的。

可变字体多字重场景下更要用比例、不能用绝对值：同一个字在 Light 和 Heavy
下笔画粗细、线段长度完全不同，绝对半径在细字重上可能完全看不出来，在粗
字重上可能把线段整个吃掉。

## 3. "连续的一笔"要求整条路径的曲率连续变化，不是"两头切线对上就行"

这是"了"字从续九改到续十一，花了四轮才吃透的教训，细节见
`docs/evidence/README.md` 第 7 项和 `tools/le_slant.py` 的历史提交。核心
认知升级：

- **切线连续（G1）不等于曲率连续（G2），更不等于"看起来像一条线"**。两段
  独立构造的曲线，哪怕在衔接点上验证过"切线方向完全一致、曲率数值也调到
  同号同量级"，肉眼仍然能看出衔接处有"腰身"——因为曲率**变化的速率**
  （更高阶的连续性）在衔接点两侧仍然是两套独立公式决定的，不会自动匹配。
  这正是续十当时的做法，效果仍然被用户一眼看出"是 S 不是一条曲线"。
- **真正的单曲线，要让整条路径从构造方式上就是同一条曲线，不是事后凑数值
  让两条曲线在一点上"看起来一样"**。TrueType 二次样条的具体做法：把需要
  连续弯曲的整段路径，用同一串连续的 off-curve 控制点表示，中间不插入
  任何 on-curve"落地锚点"——这样整条路径的切线连续性由样条基本性质保证
  （对任意一串连续 off-curve 点，相邻两段在隐式中点处的切线恒等，这是能
  解析证明的几何事实，不依赖控制点具体怎么摆），根本不存在需要"数值核验/
  搜索凑曲率"的衔接点，因为压根没有独立的两条曲线。
- **先确认某个"衔接点"是不是真实设计意图，再决定要不要保留它**：续十一
  发现此前几版当"落地锚点"用的那个点，在原始未改造几何里其实曲率为零、
  只是一条直线中途路过的点，不是真实的设计转折——合并掉它不会丢失造型。
  改之前量一下这个点真实的曲率/切线角色，别假设"现有的点都不能动"。

## 4. 一条曲线的笔画宽度可以渐变，但必须是平滑单调的，不能有局部反复

筑紫的笔画末端常有加粗/渐变（比如竖笔接近钩尾处变粗），这是正常设计表现，
不是缺陷。本仓库的判断标准不是"宽度处处相等"（那是更强、但不必要、且会
引入拼接缝的约束），而是**沿笔画方向采样宽度，变化必须平滑单调，不能有
局部的凹陷/鼓包/反复折返**——这才是"一条连续渐变的笔画"该有的样子，用
数值抽样（沿纵轴每隔一定距离测一次轮廓间距）去确认，不要只靠肉眼在正常
字号下扫一眼。

## 5. 判断"死角""机械感"的具体标准：两个转折挤在很短距离内

"了"字最早的死角问题，根子不是某一个转折角度本身不自然，是**两个转折点
（横转竖的衔接点 + 竖笔自己的直角拐角）挤在一小段很短的距离里**，叠加
起来才显得生硬。单独看任何一个转折点，可能都不算离谱；多个转折扎堆在
短距离内才是"死角""机械"观感的来源。改的时候要看"这一片范围内转折点的
密度"，不是只看单个角度数值。

## 6. 先修复结构，再调参数；结构错了，参数怎么调都没用

续九/续十反复调整"弓起幅度""控制点臂长"这些参数，每次都能让问题"看起来
好一点"，但治标不治本——根子是"用两条独立曲线拼接"这个结构选择，参数
调整空间再大也跳不出"两条曲线"的框架，直到续十一换成"同一串连续控制点"
这个结构才真正解决。**先判断问题是不是结构性的**（比如"这是不是在拼接两
个本该是一条的东西"），不要在错的结构上反复试参数——这是本轮最大的时间
浪费来源。

## 7. 验证顺序：几何数值 → 视觉渲染 → 完整流水线回归，三步都不能跳

本仓库 `docs/evidence/README.md` 开头定的规矩："配置层核对过不等于渲染层
看过"。对改字形这件事，具体展开成三步，缺一步都可能把错误带到下一轮：

1. **几何数值核验**：改完当场用代码算关键量（切线方向、曲率符号/数值、
   笔画宽度），不要只凭肉眸猜"这样应该是对的"。
2. **视觉渲染核验**：数值对，不代表肉眼看着顺眼——务必在正常字号 + 放大
   裁切两个尺度下都截图看一遍，尤其放大裁切能看出正常字号看不出的波浪/
   瑕疵。
3. **完整流水线回归**：改动不能只在孤立脚本里验证，要跑完整的
   `dian_box_compress → le_slant → foot_trim → hook_cut → vf_round
   --corners --skip-caps-json` 流水线，确认改动没有在下游环节（比如
   `hook_cut.py` 的闸门检测）引出新的、看起来无关的副作用；且必须用
   "参照字重判一次、套用到全部字重"的方式验证跨字重一致（不能三档字重
   各自独立判断，历史上这样做崩过 `plan_safety()`）。

## 8. 旧证据的失效是被动的，必须主动排查，不能等用户发现

截图/图片一旦生成，画面内容是写死的；底层代码改了，旧截图不会跟着更新，
但文档如果继续引用它，就是在传递过期信息。**改任何一处底层几何代码之后，
要主动检查"目录里还有没有别的截图画的是这个字/这个工具的旧状态"**，不能
只删跟当次改动"看起来直接相关"的那一两张——2026-10-17 的审计就是因为
只删了跟"了"字直接相关的图，漏了十几张实际上同样过期的 10-13/10-15 旧图
（国/电/七/九的箱体、端头，以及连带"了"字本身过期的两张整体回归图），
被主人指出"13号后的还没清"才发现这个遗漏模式。以后的检查方法：对每张
截图问一句"它画的那个字/那个工具，自截图日期之后有没有再被改过"，答不
上来的，现场用当前代码重新渲染一遍比对，而不是凭日期戳或者"没人提起"
就默认它还成立。
