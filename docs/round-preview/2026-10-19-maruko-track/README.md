## 1. 马路口 vs 文渊 vs Selfrounds 直接对比

当时曾有一张沙箱对照图（已于 2026-10-22 按用户要求清理）：第1列字标，第2列马路口原字，第3列文渊原字（未处理），第4列为当时的 Selfrounds 成品。旧图的文字观感记录认为马路口原字比当时处理结果更和谐，圆角更饱满、收笔更干净；此为历史目视结论，不代表当前字体状态。

## 2. 事实核验（不是凭印象判断）

拉取官方仓库 `max32002/maruko-gothic` 的 README 与 SIL OFL 1.1 许可证确认：

- **许可**：SIL OFL 1.1，可自由商用改作，改作后须同样以 OFL 发布——跟文渊一样，走
  本仓库现有"保留名"规则即可，没有法律障碍。
- **作者自曝是 AI 生成、非专业**，原话："目前字体几乎都是电脑使用 notosans 推论为
  zen maru 产生的字形，所以很粗糙，不建议使用在高解析度的输出，文字大小超过 48px
  会看出破绽，直线可能变阶梯形狀(staircase)，期待好心人二次创作，产生更高品质的
  版本。"
- **字重覆盖**：SC 版只有 Light/Regular/Medium 三档静态字重，没有 VF，也没有
  Bold/Black（JP 版才有全套）。跟本仓库"主字体须为含 wght 轴 VF"的硬约束有缺口，
  主人已确认现阶段先接受静态字重做原型，不急着补齐 VF。

## 3. 几何核验：量化"阶梯感"问题的真实成因

直接读取 `glyf` 表坐标核对（不是靠渲染截图猜）：

- "回"字马路口版 117 个点，文渊同一个字只要 20 个点，密度差 6 倍。
- "了"字的点序列里有好几段 **2~6 个"纯控制点"(off-curve) 连续堆叠**、中间没有真正
  落笔的锚点——这是自动描摹/矢量化工具的典型指纹（一条本该一笔到底的长弧线被切成
  一堆首尾相连的短弧拼出来），不是手工画字"一条视觉弧线对应一个控制点"的做法。

## 4. 排除神经网络方案

主人先后提出 zi2zi（`kaonashi-tyc/zi2zi`）和 HanziGen（`wangwenho/HanziGen`）两个
AI 造字项目作为"重写马路口"的可能路线，均已查证并排除，原因是沙箱硬件限制，不是
技术方向本身有问题：

- **zi2zi**：Python 2.7 + TensorFlow≥1.0.1 + CUDA/cudnn（早已过时的依赖链），预训练
  模型托管在 Google Drive（沙箱出站网络白名单不含该域名，连不上）。
- **HanziGen**：VQ-VAE + 潜在扩散模型（LDM），官方明确要求"至少 4GB VRAM 的 NVIDIA
  显卡 + CUDA 11.8 以上驱动"，且不提供预训练权重，每个目标字体都要独立训练。
- 本沙箱 `nvidia-smi` 不存在、无任何 GPU，2 核 CPU、3.8GB 内存——两个方案都在最基本
  的硬件门槛上就被卡死，换哪个具体仓库都一样。主人确认沙箱外也没有可用 GPU 机器，
  这条线正式搁置（不是否决方向，只是当前环境做不到）。

## 5. 改用经典几何算法：`tools/curve_simplify.py`（原型，已验证可行）

不训练模型，写了一个"自适应单二次贝塞尔拟合"工具（思路接近 Potrace/Schneider 曲线
拟合，但只产出 TrueType 原生二次贝塞尔）：

1. 把每个轮廓按真实曲线形状密集采样成折线（忠实于形状本身，不受原始控制点疏密影响）。
2. 闭合轮廓版 Douglas-Peucker 找关键拐点，切出若干段。
3. 每段先试"整段一条直线"，不行就最小二乘拟合"整段一条二次贝塞尔"，拟合误差超过
   阈值就在最大偏差点切开递归细分——该直就直、该一条弧线就一条弧线，不会像自动
   描摹那样见到采样噪声就跟着多插点。

## 6. 主人反馈"粗细不统一/粗糙/笔画比例不和谐"的量化核验（2026-10-19，文渊停做后转入）

主人明确指示"文渊不做了，专推马路口"，并指出文渊的问题是粗细不统一、做工粗糙、笔画比例
不和谐。在转向马路口之前，先把这句话从印象判断变成数字，确认马路口本身是否也有同样的
毛病（而不是默认马路口没问题）。

**工具**：`tools/stroke_width_audit.py`（数值表）+ `tools/stroke_width_heatmap.py`（可视化）。
做法：轮廓展平成折线 → 按有向面积正负号做填充+镂空光栅化 → `scipy` 距离变换 + `skimage`
骨架化，取骨架上每点的局部宽度（距离×2），排除分叉点/画布边缘，统计均值/标准差/变异
系数（CV）。

**字符集**：63 字（`07-笔画宽度量化-3档字重-63字.txt`），覆盖横竖撇捺点钩转折 + 高频复杂字，
不是此前 13 字曲线精简那个小回归集，避免"小样本看着行就当整体行"（主人此前反复强调的
覆盖面问题）。

**结果（Light / Regular / Medium 三档字重一致）**：

- 跨字均宽变异系数只有 0.035~0.051——同一字重下，不同字"整体平均笔画粗细"相当接近，
  不是不同字之间随机忽粗忽细。
- 但**单字内部**变异系数均值 0.07~0.10，最高到 0.177（`木`/`林`/`森`/`绣`/`道`/`美`/`暖`
  这类含撇捺斜笔的字排在最前）。当时的 Light/Regular/Medium 三档热力图已于 2026-10-22 清理；文字记录总结其色阶为：**横竖笔画约65~70 units，撇捺斜笔系统性更细
  （约55~62 units），笔画交叉点又系统性偏红更粗（超80甚至90+）**，三档字重同一个规律都
  成立，不是单一字重的偶然现象。

**结论**：主人说的"粗细不统一、笔画比例不和谐"，在马路口身上确实存在，而且是可复现、
跨字重一致的系统性问题——根源大概率是作者自己说的"notosans 推论 zen maru"自动描摹链路，
对不同角度的笔画没有保持统一的垂直于笔画方向的宽度（这也是 README 第3节"阶梯感"问题的
同一个病根：工具只管形状拓扑，不管笔画粗细这个字体设计维度）。`tools/curve_simplify.py`
只做"点数精简/形状保真"，不处理笔画粗细。2026-10-20 的首个逐字中位宽原型降低了单字内部 CV，
但没有改善跨字 CV；按主人选择优先处理跨字一致性后，又测试了纯共享目标，并对几何失败字形回退。
新一轮在 63 个审计项上降低了跨字 CV，但仍只是实验，不能视为生产级修复；方法、限制与数据见
`09-笔画宽度中轴试验-3档字重-63项.txt`。

### 2026-10-20：63 项中轴等宽原型（实验，不接生产流水线）

输入集与基线相同，为 63 个审计项、62 个不同字形（`国`重复计入两次）；原型只对每个不同字形
处理一次。`tools/stroke_width_normalize_prototype.py` 用每个字自己的骨架局部宽度中位数作为
统一目标；高分辨率光栅边界再由 `curve_simplify.py --tolerance 2.0 --seg-len 2.0` 重建。另跑
`--mode roundtrip` 控制组：相同光栅/重建步骤但不改宽度，用于区分算法变化和光栅管线本身的影响。

| 字重 | 跨字 CV（原字 / roundtrip 控制 / 中位宽原型） | 单字内部平均 CV（原字 / 控制 / 原型） | 单字内部最大 CV（原字 → 原型） |
|---|---|---|---|
| Light | 0.035 / 0.041 / 0.043 | 0.097 / 0.102 / 0.065 | 0.176（森）→0.107（绣） |
| Regular | 0.040 / 0.042 / 0.042 | 0.073 / 0.078 / 0.054 | 0.162（木）→0.105（木） |
| Medium | 0.051 / 0.053 / 0.053 | 0.078 / 0.082 / 0.058 | 0.177（木）→0.141（森） |

- 三档的单字内部平均 CV 相对原字下降约 26%–33%；62 个不同字形 × 三档的自交检测均通过，
  但这只排除了轮廓自交，不证明字形设计正确。
- 跨字 CV 没有改善：相对原字为 0.043/0.042/0.053；与 roundtrip 控制相比，Light 增加
  0.002，Regular/Medium 持平。Light 的一部分变化来自光栅重建本身（控制组已从 0.035 升到
  0.041），所以不能把全部变化归因于等宽算法。
- 当时曾有同流水线 13 字沙箱视觉对照（图像已于 2026-10-22 清理）；文字结论只支持“代表字没有明显整体变形”的初步观察，不等于已目视检查全部 63 项，更不等于真机/全字体验证。
- **范围结论**：这一版逐字中位宽原型只证明了"单字内部宽度离散度可下降"；它没有改善跨字 CV，
  也没有处理全字体。后续跨字共享目标试验单独记录在下一小节。

### 2026-10-20：跨字共享目标 + 几何回退（实验，不接生产流水线）

主人选择优先降低跨字 CV，并接受不同字的平均笔画宽度可能变化。对每个字重，先取 62 个字的局部
中位数中位数作为共享目标，使用 `global_strength=0`。共享目标 Light/Regular/Medium 分别为
37.03/62.01/87.94 font units。几何复核发现 Regular `文` 自交，因此只对它回退到自身逐字中位数
目标（63.50 units）；Light 与 Medium 无需回退。等权 50% blend 也做过中间试验，但跨字 CV 降幅较小，
且 Medium `森` 需要回退，故最终比较采用纯共享目标 + 单字回退。最终 62 字形×3 档自交检查均通过。

| 字重 | 跨字 CV：原字 / 控制 / 逐字中位宽 / 共享目标+回退 | 单字内部平均 CV：原字 / 控制 / 逐字中位宽 / 共享目标 |
|---|---|---|
| Light | 0.035 / 0.041 / 0.043 / **0.028** | 0.097 / 0.102 / 0.065 / **0.065** |
| Regular | 0.040 / 0.042 / 0.042 / **0.018** | 0.073 / 0.078 / 0.054 / **0.052** |
| Medium | 0.051 / 0.053 / 0.053 / **0.017** | 0.078 / 0.082 / 0.058 / **0.058** |

- 跨字 CV 相对逐字中位宽分别下降 0.015/0.024/0.036；单字内部平均 CV与原中位宽方案接近，但最大 CV 并非每档都更好。逐字目标设置改变量约为 Light −10.4%…+5.6%、Regular −7.3%…+12.7%、Medium −11.8%…+18.8%；审计所得逐字平均宽度相对原字的实际变化范围分别为 Light −8.5%（一）…+8.5%（木）、Regular −8.7%（十）…+12.9%（雪）、Medium −10.9%（一）…+15.2%（雪）。
- 三档 62 个唯一字形共 186 项均通过 `check_self_intersect.py`；这只排除单轮廓自交。当时的 13 字三档原字/共享目标沙箱对照图已清理；文字记录显示样本选了多种变化较大的字，但不等于 63 字视觉验收或真机验证。
- **范围结论**：这是一个降低样本跨字 CV 的实验原型，不代表全字库修复或生产方案；输入、统计、命令和限制见 `09-笔画宽度中轴试验-3档字重-63项.txt`。输出仍只在 `/tmp`，不接 `build.py` 或发布。

### 栅格分辨率敏感性

同一工具另以 800px 跑了一次作为压力对照。与 1200px 相比，分支数量在 Light `21/63`、Regular `25/63`、Medium `32/63` 个样本项上不同；但总中心线长度的逐字绝对相对变化中位数分别只有 `0.18% / 0.47% / 0.36%`。这说明**总长统计较稳定，但骨架分支拓扑不稳定**；以分支为单位的字内 CV 和方向分组跨字 CV 仍需更可靠的中心线/笔画识别后才能作为优化目标。复现 1200px 基线：

```sh
  --font Light=/tmp/selffont-maruko/Light.ttf \
  --font Regular=/tmp/selffont-maruko/Regular.ttf \
  --font Medium=/tmp/selffont-maruko/Medium.ttf \
  --px 1200 \
  --out-csv docs/round-preview/2026-10-19-maruko-track/11-centerline-length-baseline-63-items.csv \
  --out-md docs/round-preview/2026-10-19-maruko-track/11-centerline-length-baseline-63-items.md
```

## 9. 2026-10-21：筑紫中轴驱动的马路口轮廓预览

用户指出当前轮廓仍不像筑紫或马路口。核实生产默认依然是 WenYuan Rounded VF；前面的中心线审计没有改轮廓。随后新增研究工具 `tools/stroke_centerline_rebuild_prototype.py`：使用筑紫 A 圆 D 静态 TTF 的高分辨率中轴作为归一化结构参考，在马路口 Regular 字面框中按 Light/Regular/Medium 的全样本中位笔宽重建 62 个唯一字的静态轮廓。工具不逐点搬运筑紫外轮廓；输出仅作设计方向预览。
