# 马路口（Maruko Gothic）线：评估 + 曲线精简原型（2026-10-19）

## 背景

主人提出"两条都做"：文渊线（现有 Selfrounds 五工具流水线）继续推进，同时另起一条
"重写马路口"的线做对比。本目录记录马路口这条线目前的进展。

## 1. 马路口 vs 文渊 vs Selfrounds 直接对比

见 `01-maruko-vs-wenyuan.png`：第1列字标，第2列马路口原字，第3列文渊原字（未处理），
第4列是当时的 Selfrounds 成品。肉眼看马路口原字确实比我们当时的处理结果更和谐——
圆角更饱满、收笔更干净。

## 2. 事实核验（不是凭印象判断）

拉取官方仓库 `max32002/maruko-gothic` 的 README 与 SIL OFL 1.1 许可证确认：

- **许可**：SIL OFL 1.1，可自由商用改作，改作后须同样以 OFL 发布——跟文渊一样，走
  本仓库现有"保留名"规则即可，没有法律障碍。
- **作者自曝是 AI 生成、非专业**，原话："目前字体几乎都是电脑使用 notosans 推论为
  zen maru 产生的字形，所以很粗糙，不建议使用在高解析度的输出，文字大小超过 48px
  会看出破绽，直线可能变阶梯形狀(staircase)，期待好心人二次创作，产生更高品质的
  版本。"
- **字重覆盖**：SC 版只有 Light/Regular/Medium 三档静态字重，没有 VF，也没有
  Bold/Black（JP 版才有全套）。跟本仓库"主字体须为含 wght 轴 VF"的硬约束有缺口，
  主人已确认现阶段先接受静态字重做原型，不急着补齐 VF。

## 3. 几何核验：量化"阶梯感"问题的真实成因

直接读取 `glyf` 表坐标核对（不是靠渲染截图猜）：

- "回"字马路口版 117 个点，文渊同一个字只要 20 个点，密度差 6 倍。
- "了"字的点序列里有好几段 **2~6 个"纯控制点"(off-curve) 连续堆叠**、中间没有真正
  落笔的锚点——这是自动描摹/矢量化工具的典型指纹（一条本该一笔到底的长弧线被切成
  一堆首尾相连的短弧拼出来），不是手工画字"一条视觉弧线对应一个控制点"的做法。

## 4. 排除神经网络方案

主人先后提出 zi2zi（`kaonashi-tyc/zi2zi`）和 HanziGen（`wangwenho/HanziGen`）两个
AI 造字项目作为"重写马路口"的可能路线，均已查证并排除，原因是沙箱硬件限制，不是
技术方向本身有问题：

- **zi2zi**：Python 2.7 + TensorFlow≥1.0.1 + CUDA/cudnn（早已过时的依赖链），预训练
  模型托管在 Google Drive（沙箱出站网络白名单不含该域名，连不上）。
- **HanziGen**：VQ-VAE + 潜在扩散模型（LDM），官方明确要求"至少 4GB VRAM 的 NVIDIA
  显卡 + CUDA 11.8 以上驱动"，且不提供预训练权重，每个目标字体都要独立训练。
- 本沙箱 `nvidia-smi` 不存在、无任何 GPU，2 核 CPU、3.8GB 内存——两个方案都在最基本
  的硬件门槛上就被卡死，换哪个具体仓库都一样。主人确认沙箱外也没有可用 GPU 机器，
  这条线正式搁置（不是否决方向，只是当前环境做不到）。

## 5. 改用经典几何算法：`tools/curve_simplify.py`（原型，已验证可行）

不训练模型，写了一个"自适应单二次贝塞尔拟合"工具（思路接近 Potrace/Schneider 曲线
拟合，但只产出 TrueType 原生二次贝塞尔）：

1. 把每个轮廓按真实曲线形状密集采样成折线（忠实于形状本身，不受原始控制点疏密影响）。
2. 闭合轮廓版 Douglas-Peucker 找关键拐点，切出若干段。
3. 每段先试"整段一条直线"，不行就最小二乘拟合"整段一条二次贝塞尔"，拟合误差超过
   阈值就在最大偏差点切开递归细分——该直就直、该一条弧线就一条弧线，不会像自动
   描摹那样见到采样噪声就跟着多插点。

- **构建层**：`tools/check_self_intersect.py` 对精简后的 Light/Regular/Medium 三档
  字重、13 字全部通过，没有引入自交——证据见本目录 `04-自交检测-3档字重.txt`。
- **渲染层（沙箱渲染，不是真机证据）**：`02-curve-simplify-13chars.png`——13 字整体
  轮廓跟原始版本肉眼基本看不出差别，点数却少了四成以上（这张图只覆盖 Regular 一档）。
  **`05-curve-simplify-3weights-13chars.png`——Light/Regular/Medium 三档字重全部覆盖**
  的原始 vs 精简对比（每档都是"原始"紧跟"精简"两列，共7列），确认三档字重分别都是
  真实存在的不同粗细（`usWeightClass` 300/400/500，不是同一份文件重复），且三档的
  精简结果都跟各自原始版本肉眼一致。这张图跟 `03-curve-simplify-tolerance-sweep-
  hui.png` 一样，都是 fontTools 直接画出来的，只证明字体文件本身的几何形状，不代表
  任何设备上的实际显示效果，真机渲染这一层还是空白。
- **目视推断（不是量化判断）**：容差扫描（`03-curve-simplify-tolerance-sweep-hui.png`，
  针对"回"字左上角放大）：容差 3/5/8/12 时整体形状保持良好，原始版本在 (220,685)
  附近有一个自动描摹留下的小凹痕，容差 12 时这个凹痕在图上看不见了；容差推到 18
  时内框拐角开始出现肉眼可见的多边形化（削过头的信号），所以最终参数定在 8~12
  之间。"凹痕被吸收掉"这一句是盯着截图做的目视判断，没有做逐点像素级误差量化，
  按规矩不能说成"已验证"，算推断。
