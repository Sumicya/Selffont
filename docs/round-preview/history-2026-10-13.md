# 历史记录：自制圆体第一个真实可装预览（2026-10-13）

> 本文保留旧版 Selfrounds 圆角流水线的历史说明；部分产物和截图已不在仓库中。当前状态与筑紫 A 样稿入口见 [`README.md`](README.md)。

这不是第三方字体、不是文渊圆体、不是局部放大图。这是本仓库自己跑出来的圆角化产物。

**2026-10-17 改名**：产品/家族名统一改为 **Selfrounds**（原 `Selffont Round SC`/`SelffontRoundSC-VF.ttf`）。
下面"文件"一节按新名字描述以后新构建的产物；历史 bug 记录章节里出现的旧文件名
（`SelffontRoundSC-VF.ttf` 等）是当时真实发生的事实，原样保留，不回填改名。

## 文件

- `Selfrounds-VF.ttf`——**可变字体**，`wght` 100–900 连续可调，装一个文件等于装全部字重。真机/电脑装上即可用；用支持可变字体的看图工具（Photos 的字体预览、FontGoggles、Chrome 字体设置等）能看到拖动字重滑块时字形连续变化。
- `Selfrounds-Regular.ttf`——同一产物的 400 字重静态实例，给不认可变字体的老工具用。
- `round.designspace`——构建这个 VF 用的 fontTools designspace 源文件，`tools/vf_round.py` 产出的 7 个字重静态实例按这份 designspace 被 `fontTools.varLib.build` 合并。

## 从哪来、怎么做的

源字体：**文渊黑体（WenYuanSansSC）**，取自 `github.com/takushun-wu/WenYuanFonts`（OFL）。取的是仓库里真正的可变字体 `vf/WenYuanSansSCVF.ttf`（`git/blobs` API 直接按文件取，不是会在沙箱里卡死的 release zip 资产），用 `fontTools.varLib.instancer` 钉出 Thin/Light/Regular/Medium/SemiBold/Bold/Heavy 七个静态实例——这七个实例互相之间逐字形点数/点序完全一致（已验证：35139 个非空字形 0 处不同），这是后面还能合回可变字体的前提。

圆角化：`tools/round.py`（从本仓库 2026-09-26 的 `bcab792` 版取回，`tools/vf_round.py` 包一层让它能在多字重之间共用同一套"切哪一刀"的结构判断，而不是每个字重各自独立判断——独立判断会导致不同字重切出来的点数不一样，没法再合成可变字体）。

圆两类地方：
1. **自由端头**：笔画的真正末端（横画两端、竖画两端、撇捺尖锋）。
2. **直角拐角**（这一版新加）：两条长直线之间的凸角，比如"国/回/田"外框自己的四个角、内部方块的四个角——仿筑紫"逢角必圆"，不再只圆端头。T 形接口留下的凹切口（绕行方向判断出来的凹角）仍然一律不碰，不产生凸起，这条原则没变。

旧版说"筑紫连外框直角也会带一点圆，咱们目前没做"——这一版把这个差距补上了（`tools/vf_round.py` 的 `--corners` 开关，本预览默认打开）。

## 这一版（加拐角）过程中发现并修了三个真 bug

**都是在测"直角拐角"这一步时顺带发现的，前两个其实是旧版（端头-only）就已经带着的问题，不是拐角功能才有的：**

1. **端头鼓包误伤被盖住的笔画**：判断"这段直边算不算该圆的自由端头"只看长度/角度，没看这段边此刻是不是已经被同一字形里另一条笔画盖住了——比如"国"字里"玉"中间那一竖，为了和横画叠压不露缝会故意多插一截进横画里；这一截独立看完全符合"端头"的几何特征，但削圆之后鼓出来的半圆会从盖住它的横画边缘探出头，变成贴在横画上的一个小圆点/小尾巴（"国/田"等字复现过）。修复：削圆前用环绕数（winding number）测一下这段边外侧贴着的一小步是不是已经被整个字形的其它轮廓盖住，盖住了就跳过。
2. **可变字体跨字重套用固定半径会自交**：端头/拐角"切哪一刀"只在参照字重（Regular）上判一次，再原样套到其它字重——但同一处笔画在粗字重（Heavy）下相邻线段可能比参照字重短很多，固定的削圆半径会探出线段本身，削出来的弧自我交叉，渲染出一团乱线（Heavy 字重"电"字的钩尖复现过）。修复：削圆半径按当前字重自己的线段长度封顶，不再直接信一个跨字重通用的固定值。
3. **两个拐角紧挨同一截短连接段会在接缝处留小凹痕**：钩笔常见——两头各是一个 ~90° 拐角、中间就隔几十到一百多单位的短连接段，哪怕半径收得很小，两段独立算的圆弧在中间碰头时方向对不上，还是会留一个肉眼可见的小凹痕。修复：这种"双拐角紧贴"且连接段短的情况，两头都不圆，保持原来的尖角——跟本仓库一路的"不确定就不碰"是同一个原则；像"国/回"外框那种两个拐角隔着一整条长边的情况不受影响，照常圆。

（另外，旧版 `round.py`〔`bcab792` 定版〕在横画/捺画这类"长直线接自由端头"的笔画上会把直线和圆弧硬并成一整条二次曲线，渲染出来是一根细刺或一个扁椭圆的问题，`木`/`大`/`永`/`示` 复现过，这是更早一版就修过的，这次没有复发；修复前后对比截图已按 2026-10-17 S6 审计原则删除（问题早已修完定型），当前效果此前见 `docs/evidence/2026-10-13-round-py-效果核验.png`（该图已按 2026-10-18 "旧图全清" 删除）。）

## 覆盖范围：GB2312 + 拉丁，不是全量 CJK

`TODO.md` 定的目标是全量 CJK。沙箱只有 4GB 内存，七字重 × 35225 个字形（全量 CJK）一起喂给 `varLib.build` 会被 OOM-killed（有记录：`dmesg` 里 `Killed process ... python3 ... anon-rss:3884844kB`）。这一版先把字符集收到 GB2312（7445 个汉字/符号）+ 拉丁 + 常用标点再合并，合并顺利跑完，产物是这里这份 VF。要扩到全量 CJK，需要换一台内存更大的机器构建，或者把合并过程按字形分批做（`varLib.build` 本身不支持分批，需要自己拆 `gvar`/`glyf` 分段合并再拼接，这是下一步要做但这次没做的工程量，不是"再问一轮就能有"）。

## 关于筑紫

构建没有用筑紫的任何字形数据。`方正FW筑紫A圆` 的一份网页子集 TTF（`github.com/Aphcity/aphcity-assets`，1345 字形，商用需授权）只在本机 `/tmp` 下被当设计参照打开看过（端头/角部处理方式），从未写进这个仓库、从未提交。当时的对比截图已按 2026-10-17 全目录审计原则删除（早于后续几何修复，画面已不代表当前状态）；筑紫参照图此前留存的是 `docs/evidence/2026-10-16-筑紫了字真实轮廓放大分析.png`——原按"外部参照、时效性不随本仓库代码变化"不受常规清理影响，但 2026-10-18 主人明确要求"旧图全清"，覆盖了这条个例豁免，该图已一并删除；文字结论（筑紫是"一笔连续扫过去、钩尾位置整体偏移"的单轮廓结构）仍然成立，只是不再有对应截图。

## 这一版还没做（如果要往生产线上走）

- 全量 CJK 覆盖（见上，内存问题）。
- 度量归一到基础包 Roboto 空壳行度量（`build.py` 构建期会守卫这条，这版还没对齐）。
- `--font` 可选项接入 `build.py`。
- 真机渲染验证（目前只有沙箱 FreeType/PIL 渲染，这是开发期调试证据，不是真机证据，不能混用——按本仓库证据分层约定）。
- 拐角削圆半径（`CORNER_R_RATIO`/`CORNER_R_MAX`/`CORNER_SHARED_RATIO`/`CORNER_SHORT_SHARED`）是跟筑紫参照肉眼比出来的经验值，没有逐字重逐字形穷举验证；已做的检查是：全字重 bbox 增长量抽样（最大约 90-94 单位，集中在拉丁/数字这类简单竖笔端头，量级和端头削圆本身一致，没有异常暴涨）+ 对国/回/田/电等结构代表字和"双拐角紧贴"风险场景（电的钩尖）做了放大对比，没有做覆盖全部 9624 个字形的自动化自交检测。

## 2026-10-13 续二：拐角半径 70→130（主人反馈"圆在哪都是方的"）+ 缓存失效修复

**背景**：上一版把 `CORNER_R_MAX` 定成 70 单位/1000upm，依据是"坐标确实发生了偏移"；但 70 单位换算到正常网页/设备渲染字号（约几十像素）只有几像素的圆角半径，肉眼基本看不出跟直角的区别——这是把"坐标层面变了"当成"用户能感知到变了"的误判，两者是两回事。同时发现 `docs/round-preview/` 这条实况预览链路一直用固定文件名 `SelffontRoundSC-VF.ttf`，没做任何缓存失效处理，浏览器大概率一直吃着旧字体文件的缓存，这也是主人反馈"拖 wght 都不变"的大概率根因之一。

**改动**：
- `tools/vf_round.py` 的 `CORNER_R_MAX` 从 70 调到 **130**——依据：实测 `ZhuZiAYuanJWD.ttf`（筑紫参照，本机 `/tmp` 下量的，未入库）"回"字外框拐角实际跨度约 120–130 单位，取上限对齐这个量级。
- 全 7 字重重新跑 `--corners` 管线 → GB2312 子集 → `varLib.build` 合成新 VF，字形数与上一版完全一致（9624 字形/字重），说明半径调整不改变"哪些拐角该圆"的判定，只改变已判定要圆的拐角圆多大。
- 回归检查：全字重 bbox 增长量抽样结果与半径=70 版本完全相同（最大约 94 单位，同一批端头驱动的 outlier），证明拐角削圆是"只往里切，不往外鼓"的几何操作，半径变大不会把问题从"看不见"变成"看得见却是错的"；另外对 Heavy 字重"电"字钩尖做了单独放大检查，确认半径加大后钩尖依旧没有自相交/凹陷。
- r=70 vs r=130 的放大裁切三连对比截图已按 2026-10-17 全目录审计原则删除（早于 10-15 之后的多项几何修复，画面已不代表当前状态）；130 这个数值仍然成立，可直接读 `tools/vf_round.py` 第 47 行核对。
- `index.html` 的 `@font-face` 字体 URL 加了版本号参数（`SelffontRoundSC-VF.ttf?v=20261013b`），强制浏览器在文件内容更新后重新拉取，不再依赖文件名不变时的缓存失效策略。

## 2026-10-15：全量 CJK 的 OOM 卡点定位到 `varLib.build`，验证出分批绕过方案（这里展示的预览仍是 GB2312 版，还没换成全量 CJK）

本节上面"覆盖范围：GB2312 + 拉丁，不是全量 CJK"一节记的卡点已经细查过：不是"全量 CJK 规模太大所以什么都跑不动"，`varLib.instancer` 实例化和 `tools/vf_round.py --corners` 圆角化在全量 CJK（35089 字形/字重）规模下都在本沙箱跑得动（分别约 290MiB/字重、约 1.5GB 峰值），精确卡在 `varLib.build` 的"Generating gvar"这一步——这一步直接喂七字重全量 CJK 会把内存吃到约 3.9GB 被 OOM-killed，过程中沙箱一度卡到连基本命令都要等几十秒。

验证出的绕过方案：把字形表切成 8 批（每批约 4400 个主字形，`fontTools.subset` 闭包按需带入部件），每批独立 `subset` + 独立 `varLib.build` 进程，8 批全部构建成功，cmap 并集=源字体全集（33029 码位不少不重），跨批次渲染代表字（国/回/田/电/木/大/永/示）在 wght 100/400/900 三档圆角、插值都正常——证据此前见 `docs/evidence/2026-10-15-full-cjk-batched-vf-corners-weights.png`（已按 2026-10-18 "旧图全清" 删除），脚本是 `tools/batch_vf_merge.py`。

这个方案产出的是 **8 个独立的小 VF 文件**（按字符分流到 Android fallback 链上的相邻 family），不是一个大文件——跟这份 README 开头"装一个文件等于装全部字重"的说法不一致，是用"装齐 8 个文件缺一不可"换"不切全量 CJK 覆盖、绕开内存上限"的取舍，还没问过主人是否接受。这里展示的预览（`SelffontRoundSC-VF.ttf`）本身没有变，仍是 GB2312 子集版；全量 CJK 版还没接入 `build.py`、没做度量归一、没有真机验证，详见 `TODO.md` 2026-10-15 条目。
