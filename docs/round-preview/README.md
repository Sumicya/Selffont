# 自制圆体——第一个真实可装预览（2026-10-13，已更新：加了"逢角必圆"）

这不是第三方字体、不是文渊圆体、不是局部放大图。这是本仓库自己跑出来的圆角化产物。

## 文件

- `SelffontRoundSC-VF.ttf`——**可变字体**，`wght` 100–900 连续可调，装一个文件等于装全部字重。真机/电脑装上即可用；用支持可变字体的看图工具（Photos 的字体预览、FontGoggles、Chrome 字体设置等）能看到拖动字重滑块时字形连续变化。
- `Selffont-Round-Regular.ttf`——同一产物的 400 字重静态实例，给不认可变字体的老工具用。
- `round.designspace`——构建这个 VF 用的 fontTools designspace 源文件，`tools/vf_round.py` 产出的 7 个字重静态实例按这份 designspace 被 `fontTools.varLib.build` 合并。

## 从哪来、怎么做的

源字体：**文渊黑体（WenYuanSansSC）**，取自 `github.com/takushun-wu/WenYuanFonts`（OFL）。取的是仓库里真正的可变字体 `vf/WenYuanSansSCVF.ttf`（`git/blobs` API 直接按文件取，不是会在沙箱里卡死的 release zip 资产），用 `fontTools.varLib.instancer` 钉出 Thin/Light/Regular/Medium/SemiBold/Bold/Heavy 七个静态实例——这七个实例互相之间逐字形点数/点序完全一致（已验证：35139 个非空字形 0 处不同），这是后面还能合回可变字体的前提。

圆角化：`tools/round.py`（从本仓库 2026-09-26 的 `bcab792` 版取回，`tools/vf_round.py` 包一层让它能在多字重之间共用同一套"切哪一刀"的结构判断，而不是每个字重各自独立判断——独立判断会导致不同字重切出来的点数不一样，没法再合成可变字体）。

圆两类地方：
1. **自由端头**：笔画的真正末端（横画两端、竖画两端、撇捺尖锋）。
2. **直角拐角**（这一版新加）：两条长直线之间的凸角，比如"国/回/田"外框自己的四个角、内部方块的四个角——仿筑紫"逢角必圆"，不再只圆端头。T 形接口留下的凹切口（绕行方向判断出来的凹角）仍然一律不碰，不产生凸起，这条原则没变。

旧版说"筑紫连外框直角也会带一点圆，咱们目前没做"——这一版把这个差距补上了（`tools/vf_round.py` 的 `--corners` 开关，本预览默认打开）。

## 这一版（加拐角）过程中发现并修了三个真 bug

**都是在测"直角拐角"这一步时顺带发现的，前两个其实是旧版（端头-only）就已经带着的问题，不是拐角功能才有的：**

1. **端头鼓包误伤被盖住的笔画**：判断"这段直边算不算该圆的自由端头"只看长度/角度，没看这段边此刻是不是已经被同一字形里另一条笔画盖住了——比如"国"字里"玉"中间那一竖，为了和横画叠压不露缝会故意多插一截进横画里；这一截独立看完全符合"端头"的几何特征，但削圆之后鼓出来的半圆会从盖住它的横画边缘探出头，变成贴在横画上的一个小圆点/小尾巴（"国/田"等字复现过）。修复：削圆前用环绕数（winding number）测一下这段边外侧贴着的一小步是不是已经被整个字形的其它轮廓盖住，盖住了就跳过。
2. **可变字体跨字重套用固定半径会自交**：端头/拐角"切哪一刀"只在参照字重（Regular）上判一次，再原样套到其它字重——但同一处笔画在粗字重（Heavy）下相邻线段可能比参照字重短很多，固定的削圆半径会探出线段本身，削出来的弧自我交叉，渲染出一团乱线（Heavy 字重"电"字的钩尖复现过）。修复：削圆半径按当前字重自己的线段长度封顶，不再直接信一个跨字重通用的固定值。
3. **两个拐角紧挨同一截短连接段会在接缝处留小凹痕**：钩笔常见——两头各是一个 ~90° 拐角、中间就隔几十到一百多单位的短连接段，哪怕半径收得很小，两段独立算的圆弧在中间碰头时方向对不上，还是会留一个肉眼可见的小凹痕。修复：这种"双拐角紧贴"且连接段短的情况，两头都不圆，保持原来的尖角——跟本仓库一路的"不确定就不碰"是同一个原则；像"国/回"外框那种两个拐角隔着一整条长边的情况不受影响，照常圆。

（另外，旧版 `round.py`〔`bcab792` 定版〕在横画/捺画这类"长直线接自由端头"的笔画上会把直线和圆弧硬并成一整条二次曲线，渲染出来是一根细刺或一个扁椭圆的问题，`木`/`大`/`永`/`示` 复现过，见 `docs/evidence/2026-10-13-round-py-笔画端头放大对比.png`，这是更早一版就修过的，这次没有复发。）

## 覆盖范围：GB2312 + 拉丁，不是全量 CJK

`TODO.md` 定的目标是全量 CJK。沙箱只有 4GB 内存，七字重 × 35225 个字形（全量 CJK）一起喂给 `varLib.build` 会被 OOM-killed（有记录：`dmesg` 里 `Killed process ... python3 ... anon-rss:3884844kB`）。这一版先把字符集收到 GB2312（7445 个汉字/符号）+ 拉丁 + 常用标点再合并，合并顺利跑完，产物是这里这份 VF。要扩到全量 CJK，需要换一台内存更大的机器构建，或者把合并过程按字形分批做（`varLib.build` 本身不支持分批，需要自己拆 `gvar`/`glyf` 分段合并再拼接，这是下一步要做但这次没做的工程量，不是"再问一轮就能有"）。

## 关于筑紫

构建没有用筑紫的任何字形数据。`方正FW筑紫A圆` 的一份网页子集 TTF（`github.com/Aphcity/aphcity-assets`，1345 字形，商用需授权）只在本机 `/tmp` 下被当设计参照打开看过（端头/角部处理方式），从未写进这个仓库、从未提交。对比图 `docs/evidence/2026-10-13-自制圆体与筑紫参照对比.png` 里"筑紫"那一行只是取来对照，不是产物的一部分。

## 这一版还没做（如果要往生产线上走）

- 全量 CJK 覆盖（见上，内存问题）。
- 度量归一到基础包 Roboto 空壳行度量（`build.py` 构建期会守卫这条，这版还没对齐）。
- `--font` 可选项接入 `build.py`。
- 真机渲染验证（目前只有沙箱 FreeType/PIL 渲染，这是开发期调试证据，不是真机证据，不能混用——按本仓库证据分层约定）。
- 拐角削圆半径（`CORNER_R_RATIO`/`CORNER_R_MAX`/`CORNER_SHARED_RATIO`/`CORNER_SHORT_SHARED`）是跟筑紫参照肉眼比出来的经验值，没有逐字重逐字形穷举验证；已做的检查是：全字重 bbox 增长量抽样（最大约 90-94 单位，集中在拉丁/数字这类简单竖笔端头，量级和端头削圆本身一致，没有异常暴涨）+ 对国/回/田/电等结构代表字和"双拐角紧贴"风险场景（电的钩尖）做了放大对比，没有做覆盖全部 9624 个字形的自动化自交检测。
