# 拉丁间距三套方案（2026-11-23 实测）

母版 upm 1000，字母 52 个（A–Z a–z）。所有读数用同一把尺：
**墨隙 = 前字右白 + 后字左白 + GPOS kern**，字形包围盒由 `glyf.recalcBounds()` 取。

![三套方案真排对照](2026-11-23-latin-spacing-options.png)

![关键字对特写](2026-11-23-latin-spacing-pairs.png)

## 起点（母版现状）

| 项 | 数值 |
|---|---|
| 字母左侧空（lsb）中位 | 47.0 |
| 字母右侧白（rsb）中位 | 47.5 |
| 每侧合计 | **94.5 / 1000 em** |
| 字母×字母墨隙中位 | 111 |
| 已重叠对（< 0） | **63 对** |
| 过紧对（< 8） | 71 对 |
| 最紧一对 | `FJ` = −93（kern −150） |

母版自己就有 63 对重叠——这不是这次要修的，是既有底数。

## 三套方案

| | 方案 B-lite | 方案 B | 方案 A |
|---|---|---|---|
| 命令 | `--latin-gap 60` | `--latin-gap 47` | `--latin-gap 30` |
| 改什么 | 只压富余过大的字形 | 每侧削到 47 | 每侧削到 30 |
| 左侧空中位 | 47.0（未变） | 47.0 | **30.0** |
| 右侧白中位 | 47.5（未变） | 47.0 | **30.0** |
| 字母 advance 中位 | 553 | 540 | 506.5 |
| 墨隙中位 | 97 | 85 | **60** |
| 重叠对 | **78** | **78** | **106** |
| 过紧对（< 8） | 85 | 85 | 132 |
| kern 重写条数 | 6 | 18 | 24 |
| 输出体积 | 19,968,536 B | 19,968,508 B | 19,968,492 B |

**关键读数**：三套方案的重叠对都**比母版多**（63 → 78 → 106）。原因是
`tools/slim_mother.py` 的 kern 重写只覆盖母版 GPOS 里**已有条目**的对；
压紧后新产生的重叠（如 `LY`、`TA`、`YA`）母版本来就没 kern 记录，
于是压得越紧、撞得越多。**「碰撞全为 0」的说法不成立**——上一版文档里
的这句实测已证否。

## 逐方案判读

**方案 B-lite（gap 60）**：302 个字形里只动了富余过大的那批，整行宽度基本不变
（英文正文 1053 → 1034 px，−1.8%）。看不出差别，等于没做。**否**。

**方案 B（gap 47）**：左侧空从 47.0 起已经不再下降（母版中位就是 47），
所以只有右侧被削。英文正文 1053 → 1014 px（−3.7%），大写对 −1.0%，
中英混排 −2.0%。重叠 63 → 78。**左右不对称，字偏左**。

**方案 A（gap 30）**：两侧都到 30，合计 60 / 1000 em（比现状紧 37%）。
英文正文 1053 → 961 px（**−8.7%**），大写对 779 → 755 px（−3.1%），
中英混排 1163 → 1108 px（−4.7%）。但重叠 63 → **106**，过紧 71 → 132。
`FJ` / `Qj` / `YJ` / `fj` / `AT` / `LY` / `To` 的特写里肉眼可辨地更挤。

## 结论

三套都**不能直接上**，原因同一：`slim_mother.py` 只改母版已有的 kern 条目，
新产生的重叠无人补。

要真做，必须先补一步：**对全部 52×52 = 2,704 对重算 kern 并写入 GPOS**，
再按 `--min-ink` 兜底。这一步现成的 `tools/kern_measure.py` 能做
（它本来就是拿 HarfBuzz 真排母版量白），但它写的是 `kern_targets.bin`
供构建期用，不是直接改母版 GPOS。

## 建议顺序

1. 先做 **方案 B**（只削右侧，−3.7%）：可逆、只动 advance、不碰 kern，
   `build.py --check` 19 项应仍全过。
2. 若 B 通过人眼与 `--check`，再补 kern 重算，然后跳到 **方案 A**。
3. 方案 A 单独上必须同时重算 2,704 对 kern，否则重叠从 63 涨到 106。
