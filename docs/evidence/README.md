# 验证证据

写「已验证」之前先答一句：证据在哪个文件。答不上来就只能写「推断」或「未验证」。

## 三层，各自留各自的证据

| 层 | 断言的样子 | 证据形式 | 存放 |
| --- | --- | --- | --- |
| 配置层 | 设备上的配置内容符合构建预期、模块挂上了 | 命令输出存成 `.txt` | 本目录 |
| 构建层 | 打包器行为、断言有效、产物命名 | `build.py --check` 与 CI 运行记录 | 更新日志里写明 run 号 |
| 渲染层 | 屏幕上的字形、版面、字重 | **截图 `.png`** | 本目录 |

三层的结论不许合并成一句「真机验证通过」。配置层核对过不等于渲染层看过——`grep -c` 数的是配置文件里的字符串，一个像素都不证明。「看起来没问题」也不算验证，要么是坐标/半径的具体数字，要么是能复现的脚本输出。

命名：`<日期>-<项>.png`，例如 `2026-10-07-系统字形.png`。

### 7. "了"横折转角跟竖笔死角硬接（2026-10-16，多轮迭代，历史版本全部已作废只留当前）

背景：横折转角（contour2，一条独立弧线轮廓）跟竖笔主干（contour0）在顶部
衔接点坐标重合，但衔接之后 contour0 自己先走一小段**水平直线**（到竖笔右上角），
再急转 90° 走**垂直直线**往下——两个转折挤在很短距离里，是视觉上"死角"
"机械感"的根源。这条问题改了五版，前四版都被判定不合格或实测出新 bug，
具体过程见 git log（`tools/le_slant.py` 的提交历史），这里不重复贴中间版本的图，
只记录最后站得住的结论和证据。

当前生效版本（`tools/le_slant.py`）做两件事：

1. **转角去尖角**：把顶边的"水平直线→90°角→垂直直线"换成 `vf_round.py`
   同款的拐角削圆公式（圆弧控制点取原拐角顶点，两端锚点各退/进半径 r），
   半径取**整条水平边的全长**，把整条顶边吃进弧线，衔接点直接平滑弯下去。
2. **竖笔弓形**：竖笔左右两条边在"双方都存在"的公共高度区间内，用
   **同一个 bow_amt**、**同一条 TrueType 三控制点二次 B 样条**（3 个连续
   off-curve 控制点，中间不放任何 on-curve 锚点）鼓一下，不抄筑紫坐标、
   全部现场从本字形自身的粗细/长度比例算。踩过的坑、怎么定位、怎么解决，
   详见 `tools/le_slant.py` 里 `_bow_points()` 函数文档字符串的完整记录
   （概括：强行插 on-curve 中点会在拼接处留下约 48° 的切线突变，肉眼就是
   一个尖角瘪陷；改成单段二次贝塞尔虽然曲线本身光滑了，但端点切线会偏离
   原方向约 20°，跟上下游直线段衔接处又露出新的折角；最终用 TrueType 原生
   支持的多控制点二次 B 样条才同时解决"曲线处处光滑"和"两端切线精确
   不变"这两个要求）。

- `2026-10-16-了字竖笔弓形去尖角修复后对比筑紫.png` —— Light/Regular/Heavy
  三档字重最终产物（已过 `le_slant→hook_cut→vf_round` 完整流水线）+ 筑紫 A 丸
  参照并排对比。
- `2026-10-16-了字Heavy字重竖笔放大图-去尖角后.png` —— Heavy 字重单独放大图，
  用来肉眼核对竖笔全程（转角→弓形→钩尾收口）是否平滑、有没有残留瘪陷/折角。
- 已验证（量化，非目测）：
  - 笔画宽度：密集采样（300 点/字重）验证竖笔左右边界在任意高度的间距
    在三档字重下各自恒定（如 Heavy 恒为 154 单位），弓起前后不变形。
  - 两端切线：数值验证 B 样条两端控制点方向与相邻直线段方向完全一致
    （误差为 0），衔接处不再有折角。
  - 跨字重拓扑：Light/Regular/Heavy 三档字重处理后"了"字点数/轮廓结构
    完全一致（41 点 / 3 轮廓 / `[17, 25, 40]`），可以正常喂给 `varLib.build`
    插值。
  - 下游不受扰动：`hook_cut.py` 在当前版本上三档字重切出同样的 55228 处钩、

  - "了"字本身不是任何其他字形的复合组件（0 处复合引用），改动范围完全

### 8. "七"/"九"顶端横折弯鼓成球形端头（2026-10-15，已修复）

背景：横折弯（或横折弯钩）顶端是一条独立轮廓的平头收尾，跟另一条横画十字交叉而成，本应看起来像"横捺"收束的转折，但通用的"自由端头"规则把它当成孤立端头处理，削成了突出的半圆球形鼓包。这个模式在"电/也/七/了/元/围/己/已/九/乙/园"等很多字上都有端头，但只有"七"（contour1 点16/17）和"九"（contour2 点15/16）这两处——顶端完全外露、单独一条竖钩跟横画交叉而不是互相包住——鼓包在视觉上明显突出，所占比例远超其他同类端头。

修法：复用第 5 项已有的 `skip_caps` / `force_corners` 管线，把这两处端头的点坐标加进 `skip_caps` JSON（跟 `foot_trim.py` 产出的结构完全一样），让 `vf_round.py` 的 `detect()` 跳过"判成端头"，改走拐角圆化路径——不用新写分类逻辑。

- `2026-10-15-qi-jiu-cap-bulge-fix-3weight.png` —— "七"/"九"二字，Light/Regular/Heavy 三档对比，顶端从鼓球形端头变成跟其余拐角一致的适度圆角。
- 回归：改动后 20 字×3 字重拓扑一致性检查全部 OK（见第 9 项）。

### 9. 跨字重拓扑一致性 + 最终整体回归（当前状态，覆盖以上全部修复）

`tools/hook_cut.py` 曾经对同一个字在不同字重下独立判断"切不切钩尾"，导致带钩字跨字重点数不一致，`vf_round.py` 的 `plan_safety()` 直接 `KeyError` 崩溃。改法：检测（`find_hooks()`/`detect_hook_plan()`）只在参照字重上判一次，所有字重套用同一份点序号决定——跟 `vf_round.py`/`foot_trim.py` 已经在用的模式一致。

- `2026-10-15-hookcut-11chars-3weight-final.png` —— 全部 11 个带钩字（电也七了元围己已九乙园），Light/Regular/Heavy 三档叠放，当前最终状态：钩尾干净、粗细随字重正常变化，无断线/残端/自相交。其中"己/已/乙"三字经参照字重判定后确认不需要切（它们的收尾笔画本来就是贴合的小弯钩，不是外露鼓包），三档字重下都保持一致、无需处理。
- `2026-10-15-final-20char-3weight-regression.png` —— **当前唯一有效的整体回归图**，20 个测试字（含 11 个带钩字 + 9 个口字框字：电也七了元围己已九乙园国回田日目西固困圆）× Light/Regular/Heavy 三档字重，套用上面全部修复（1、4、5、6、7、8 项）之后的最终效果。逐字看过没有新问题。
- 数值核验：对 Light(wght=100)/Regular(400)/Heavy(900) 三档实例跑完整流水线后，直接读取 `glyf` 表数出每个测试字的轮廓数、总点数，20 个测试字三档字重**全部一致**；`vf_round.py` 的 `plan_safety()` 三档字重一起跑不再 `KeyError` 崩溃。
