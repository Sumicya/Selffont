链的第一环在 Dart 层。lib/common/system_fonts.dart 全文只有三十来行：一个可注入的读取函数 systemFontFamiliesReader，默认指向 rust_api.systemFontFamilies；一个 loadSystemFontFamilies，包了 try/catch，异常时打〖1100〗一条 warning 日志并返回空表。注释写得很清楚，这个列表是「引擎在本机按名字能解析到的字体家族」，按顺序排好给选择器用。也就是说，这个列表不是从 Java 的 SystemFonts 拿的，也不是从字体文件里扫出来的，它是 Rust 侧解析配置文件得到的字符串数组。

链的第二环在 Rust 层。plugins/rust_api/rust/src/fonts/android.rs 第〖1200〗一行就是常量 FONTS_XML 等于 /system/etc/fonts.xml，families() 把这个文件整体读成字符串，失败就把路径和错误一起返回。真正干活的是 named_families：它在整个文本里逐次找子串 <family，把紧跟其后的字节取出来，若第一个字节是字母数字或下划线就跳过（这是在排除 <familysomething> 这种不存在的伪标签），然后取到第一〖1300〗个 > 之前的属性串，用 name_attribute 在里面找 name=" 并取出引号内的值。所以这个列表就是文件里所有 <family name="..."> 的 name 属性，按出现顺序排列，去重不做，<alias> 一个都不算。测试用例也印证了这一点：输入里给了 sans-serif、serif-monospace 两个命名族，一个 lang 族，一个 fallbackFor 族，一个 alias，断言输出恰好是前两个。

链的第三环是它读的〖1400〗那份文件本身。Skia 的解析器把路径写死成 /system/etc/fonts.xml（src/ports/SkFontMgr_android_parser.cpp 的 LMP_SYSTEM_FONTS_FILE，第五十一行），版本号大于等于二十一之后再追加读 /product/etc/fonts_customization.xml，字体文件的根目录取环境变量 ANDROID_ROOT 拼上 /fonts/。也就是说，FlClash 那个界面里看到的名字，和 Skia 渲染时拿到的名字集合，来源是同一份文件的同一个解析口径：一个用 Rust 手写扫〖1500〗描，一个用 Skia 自己的 parser。这个一致性很重要，它意味着「列表里有 sans-serif」这件事本身就证明那份文件被读到了，而且里面确实有 sans-serif 这个 name。
现在看你给的截图，那十三个名字是 casual、cursive、monospace、op-sans-en、osans-solid-digits、roboto-flex、sans-serif、sans-serif-condensed、SANS-SERIF-SMALLCAPS、serif、serif-monospace、source-sans-pro、sys-sans-en。我拿这些名字去我方仓库的 fonts.xml 里数，结果是：op-sans-en 零次，osans-solid-digits 零次，SANS-SERIF-SMALLCAPS 零次（模板里只有小写的 sans-serif-smallcaps）；sys-sans-en 五次，roboto-flex、source-sans-pro、zdigit 都在。再拿〖1600〗 MFGA 的原始 fonts.xml 数，前三个同样零次。MFGA 那份和我方那份的差异只有九行，是 NotoMusic、NotoEmoji、Noto-COLRv1 三个族。

把 Skia 那份源码〖3800〗再逐函数走一遍，因为这一轮真正有价值的东西全在细节里，而我前三轮都停在「大致对」的层面。

第一个函数是 SkFontMgr_Android 的构造函数。它做的事按顺序是：如果传了 custom 且不是「优先系统」模式，先解析自定义的字体配置与回退配置；如果没传 custom 或者模式不是「只用自〖3900〗定义」，再调 GetSystemFontFamilies 拿系统家族；如果是「优先系统」模式，则把自定义的追加到系统后面；最后一次性 buildNameToFamilyMap，再 findDefaultStyleSet。Flutter 的 platform_android.cc 传的是空指针，所以走的只有第二条分支，也就是纯系统家族，没有自定义。这一条把「Flutter 会不会读到别处去」这个问题彻底关掉：它读的就是系统那份，路径由〖4000〗解析器写死，没有旁路。

第二个函数是 GetSystemFontFamilies。它先拼根目录：取环境变量 ANDROID_ROOT，追加 /fonts/。然后调 append_system_font_families，这个函数先尝试解析 LMP_SYSTEM_FONTS_FILE 也就是 /system/etc/fonts.xml，记录返回的版本号；如果版本号小于零，或者解析完家族数没增加（说明文件不存在或空），就退回解析老格式的 system_fonts.xml。得到版本号之后判断：大于等〖4100〗于二十一，就去解析 /product/etc/fonts_customization.xml，然后直接返回，不再走老的 fallback 那条；小于二十一才去扫 /system/etc 与 /vendor/etc 下所有以 fallback_fonts- 开头、.xml 结尾的按语言拆分的文件。这条分支说明两件事：第一，Android 十七这种版本走的必然是第一条，也就是 fonts.xml 加 fonts_customization.xml，老的按语言拆分的文件根本不参与；第二，fonts_customization.xml 是**追加**，它不能改〖4200〗变已经在 fonts.xml 里定义好的族，只能新增或修改。这一点对我们很关键：如果想把族挂到 sans-serif 上，靠 fonts_customization.xml 里的修正指令是另一条可走的路，但那条路的语法是 fonts-modification 版本二十一，和我们现在的插入行不是一回事。

第三个函数是 addFamily。它接收一个家族对象、是否隔离、家族序号、以〖4300〗及一个用于缓存流的对象。它先看这个家族的 fallbackFamilies 是不是空的：如果不空，就逐个生成合成名字，格式是把十六进制的家族序号加上两个井号再加 fallback 六个字母。这个细节很重要，它说明带 fallbackFor 的家族在名字表里是有一个自动生成的名字的，但同时它也会进〖4400〗另一张表。接着它构造样式集：拿这个家族、扫描器、是否隔离、流缓存造一个 SkFontStyleSet_Android，然后立刻检查这个样式集的 count 是不是零，是零就直接 return，也就是**整个家族不登记**。再往下才是登记：遍历家族的 fNames，把每个名字和样式集配成一对塞进目标表；最后把样式集塞进 fStyleSets。

这〖4500〗段代码解释了一个我上一轮推理里忽略的点：判断「族在不在」的唯一标准是它至少有一个能读到的字件。count 是怎么算的？样式集构造时会把家族里每个 Font 的路径拼成完整路径去开流，开不出来的就不算。所以「sans-serif 出现在列表里」这件事，严格地证明了两层〖4600〗东西：第一层，文件被读到了（否则名字无从得来）；第二层，这个族里至少有一个字件在挂载后的文件系统里真的能打开。第二层是我上一轮没想到的，它顺手排掉了一整类假设：不可能是「整个 /system/fonts 没挂上」。

但它同时也说明另一件事：如果族里有十条字件〖4700〗、其中九条能开、我插的那一条开不了，族的 count 是九，不为零，家族照常登记，名字照常在列表里。这时候渲染时 matchAStyle 会在我那条上尝试打开、失败、跳过，最后选中设备那条 400。表现得和「没插」一模一样。这就是假设一的精确形态，也是它至今没被排除的原因——它和「插〖4800〗了但没生效」在所有外部观察上完全同形。

第四个函数是 buildNameToFamilyMap。它对家族列表里每个家族调一次 addFamily，然后再遍历这个家族的 fallbackFamilies，对每一个回退家族再调一次 addFamily，家族序号递增。这里的关键是顺序：主家族先登记，回退家族后登记。因为后面 onMatchFamily 是线性遍历比对，先登记〖4900〗的优先返回。这条顺序规则决定了：如果两份不同的家族都叫 sans-serif（一份来自 fonts.xml，一份来自 fonts_customization.xml 的追加），那么先登记的赢，也就是 fonts.xml 里的那份。这给我们一个明确的投放结论：想让某一份配置生效，不是「后写覆盖」，而是「先登记优先」。这条和我之前按文件系统覆盖顺序〖5000〗去思考的思路完全相反，值得单独记下来。

第五个函数是 findDefaultStyleSet。它只有一个硬编码名字 sans-serif，调 onMatchFamily 拿样式集，取到就停；取不到就用 fStyleSets 的第一项。fStyleSets 的顺序就是家族登记顺序，也就是 fonts.xml 里出现的顺序加 append 的顺序。这条兜底意味着：即使 sans-serif 这个名字不存在，默认族也会退到最简〖5100〗单的那个匿名族上，而那个族通常是 Roboto 的空壳。也就是说「默认族退化成 Roboto」在架构上是默认行为，不是异常。

第六个函数是 onMatchFamily。它对传入的名字做 SkAutoAsciiToLC（只把 ASCII 大写转小写，注意是非 ASCII 字节保持原样），然后在 fNameToFamilyMap 里线性找 name 完全相等的一项，找到就返回。找不到再去 fFallbackNameToFamilyMap 里找，那里〖5200〗存的是自动生成的名字和 fallbackFor。两条都找不到返回空。这里有一个必须记住的细节：这个比较是**精确相等**，没有前缀、没有包含、没有空格容忍。所以在 fonts.xml 里写 name="sans-serif " 末尾多一个空格，或者用全角字符，或者大小写混写但用的是非 ASCII，都会匹配失败。我方插入行只动 font 行〖5300〗不动 family 属性，所以这一条不是当前故障源，但它是将来改族名时必须守的规矩。
第七个函数是 find_family_style_character，整个逐字回退的核心。签名里有请求族名、名字表、样式、是否 elegant、语言标签、字符、以及一个匹配谓词。循环体做四件事：先用谓词过滤，不匹配就跳过；然后调样式集〖5400〗的 matchAStyle 拿一个面——注意这里每族只取一个面，不是我原先以为的「每族每个面都试」；接着做两道过滤，一道是语言标签（如果调用方给了非空语言标签，这个面声明的语言列表里必须有以该标签开头的，否则跳过），一道是 elegant 位（面声明的变体位要和请求的 elegant 一〖5500〗致，否则跳过）；最后才是关键——问这个面有没有这个字符的 glyph，有就返回，没有就继续下一个名字。

这四件事里，第三件最容易被我忽略，但它解释了 ColorOS 上大量 language 族的形态。那份文件里有 und-Arab variant="elegant" 和 variant="compact" 成对出现的写法，就是为这两个 elegant 取值准备的：同一个文字系统给两份面〖5600〗，一份不压扁、一份压在升降部内。如果请求是 elegant 而文件里只有 compact，这个面会被跳过，然后落到下一个名字，最后可能落空。这也解释了为什么「跳过韩文族」那条保护是必要的：本包里谚文零个，一旦我们的字件被选成韩文族的唯一面，韩文就整片豆腐，因为〖5700〗那个面没有 glyph，而族里没有第二个面可退。

第八个函数是 onMatchFamilyStyleCharacter，族的选择顺序。注释列了五层，代码也是五层，一层一层对应着 find 闭包里的五个 find_family_style_character 调用：第一层查 fNameToFamilyMap 里名字相等的；第二层查 fFallbackNameToFamilyMap 里 fallbackFor 相等的；第三层查 fFallbackNameToFamilyMap 里 fallbackFor 为空的（这一层不判名字，等于「所有匿名回退族」）；第四层〖5800〗查 fNameToFamilyMap 里名字不等的；第五层查 fFallbackNameToFamilyMap 里 fallbackFor 既不为空也不等于请求名的。然后外层还有三重循环：先按当前族名（以及空族名再跑一遍，如果当前族名非空）、再按 elegant 真假、再按语言标签从精确到父级逐层退化。

这个五层加三重循环的完整结构，是前三轮我以为自己〖5900〗懂了但其实没懂的东西。原始名和空名各跑一遍，意味着同一份文件里两套族都可能被问到：先问「名字是 sans-serif 的族」，再问「无名族」。前者的匹配谓词是名字相等，后者的谓词是 fallbackFor 为空。所以在 sans-serif 这一族里插一条 400，只在第一层有意义；一旦第一层返回了一个面（因〖6000〗为族里设备自己那条 400 也能画这个字），后面的层全部不会执行。这是「族首插入能不能赢」的全部机制：不是和我们插入的行比，而是和设备那条同权重的 400 比，谁在族里先出现。

matchStyleCSS3 的细节我上一轮只说了「同分先出现」。这一轮把话说准：它按四件事给每个候〖6100〗选面打分，一是宽度（请求宽度和面声明宽度的差），二是权重（距离），三是斜体（一致加分），四是可变的轴。同权重同斜体时，分数相同；比较写法是当前最高分严格小于新分数才替换，所以同分时先出现的保留。我们的行在族首，所以同分时我们保留。这条〖6200〗推理成立的前提是我们那条能开、能读、glyph 查询不为零。三个前提里前两个我已经承认没验，第三个更没验：如果我们的字件能开，但那个特定字符不在它的 cmap 里（比如一个很生僻的符号、一个 emoji 变体选择子、一个带轴的可变实例），glyph 是零，这个面就被跳过，落到〖6300〗设备那条。这就是「全字符覆盖」这个卖点的真正弱点所在：不是族选错了，是字符级的覆盖不足让设备兜底接管。

这一条要诚实说：本包主字体是丸ゴシック的改造版，汉字覆盖是常用区加扩展区的一部分，不是全部九万七千零四十六个码位。补充字件是几〖6400〗支符号与 emoji，也不是全量。所以真机上出现「一部分字变了、一部分没变」是完全可能的，而如果变的那部分恰好是界面上不显眼的地方，用户第一眼看到的就是「字体没变」。这个可能性我前三轮一次都没提过，因为我一直把它当成「覆盖率」这个统计指标〖6500〗，而不是当成「族首插入会输给设备」这个机制。同一个数字，用在两个地方，含义完全不同。

再看一个我一直没说清的东西：为什么「插在族首」这个方案在逻辑上必然只能赢一半。原因是 Skia 每族只取一个面。设备的 sans-serif 族里九条同权重档位全部指向同一个文件 Roboto-Regular.ttf 靠 wght 轴变化，我方插入一条 400 也在族首。对一个 400 请〖8900〗求，两条同分，我方赢。对一个 700 请求，我方那条不匹配 700（差三百），设备那条匹配 700 的轴实例（差零），设备赢。所以「插一条 400」这个设计，本质上只能覆盖常规字重的正文，标题、按钮、加粗全部回到 Roboto。这解释了为什么即使机制全对，观感上也可能「只有一部分变了」。这条是〖9000〗我这轮读代码才真正算出来的，之前几轮我一直在讨论「插哪一族」，从没算过「插哪一档」。

正确的做法应该是按字重逐档插，把 100 到 900 九档都插进族首并且都指向我方字件。可这里立刻撞上另一个事实：我方主字体是静态字体，没有 wght 轴。九档全指向同一个〖9100〗静态文件，实际效果是九档全都用同一份常规字重的笔画，加粗时由渲染侧做假加粗。这比「加粗变回 Roboto」更符合「字体整体换掉」的目标。这是一个真正的方案改动，且逻辑有源码支撑。它的代价是：族里前九条全是我方的，设备的九档全部被挤到后面，等〖9200〗于这一族的 Roboto 完全不可达。而这正是我们想要的。

但这个方案有一个必须同时处理的后果：一旦九档全占，韩文字件在该族里也全被挡掉，如果这个设备把韩文写在 sans-serif 族里而不是单独的 ko 族，韩文就豆腐。所以九档方案必须配合「字件本身含谚文」或者「九〖9300〗档只占 400 到 700 四档，留出 100、200、800、900 给设备」这种折中。前者要求换字体或加合字，后者牺牲极端字重。按规范「不破坏设备原字体行为」这条，后者更安全。
